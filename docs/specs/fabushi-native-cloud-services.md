# Fabushi native cloud services

Status: active; implementation and production acceptance incomplete
Date: 2026-10-24
Owner: existing Mahayana Platform Worker; Desktop Host service consumers; Backend public gateway

## Authority and goal
User explicitly requires removing Cursor service dependencies across Fabushi, retaining cloud automation, cloud agents and cloud file synchronization as Fabushi-owned capabilities. This supersedes historical vendor-service parity. The service state owner remains the existing Rust Worker and its PLATFORM_DB, account identity remains ACCOUNT_DB. Backend owns public gateway and deployment; Desktop owns product execution and local materialization. No parallel service/database/agent runtime is introduced.

## Current sources and ownership
Core baseline c7d0e24; Desktop baseline 7394f6dc. Core Worker has live-session authentication, durable listeners, device execution/operation journal and account infrastructure. Desktop's Worker copy includes account_agent_store, absent from Core main: source reconciliation is required before claiming canonical deployment supports file synchronization. Backend Node AccountSyncStore also has agent/file data; it is not automatically the public /v1 authority because the gateway delegates /v1 to the Rust Worker. Do not substitute source existence for production proof.

## Required service migrations
NS-R1: native automation definitions, schedules (timezone/DST/clock), trigger ingress, account/device-scoped delivery, idempotent completion, durable restart reconciliation and ACK semantics.
NS-R2: native cloud Agent launch/status/transcript/artifacts/cancel/archive/environments use existing worker/device execution owner and grants. No Cursor session, RPC or cloud dashboard required.
NS-R3: native agent/file synchronization reuses existing account state/CAS/conflict owners; preserve encryption, multipart/large-file, access, deletion, sharing and offline/restart semantics. Reconcile source owners before deployment.
NS-R4: migrate remaining model/media/search/setup/marketplace/notifications/feedback/privacy/experiments/update/telemetry consumers to existing native or local owners, removing foreign endpoint defaults and vendor credentials. Preserve feature behavior; silent disablement, placeholder success and renamed unsupported RPCs are incomplete.
NS-R5: account/session revocation, origin/issuer binding, tenant/device/grant isolation and late response generation fences apply to all operations. Never migrate foreign tokens into native auth.
NS-R6: all executable verification in GitHub Actions. Native real-service/package/network acceptance on current revisions is mandatory for complete removal, separately from schema/mocks/wasm compilation.

## Native automation control and clock (NAC-01..08)
NAC-01: extend the existing Core automation domain and PLATFORM_DB with account-owned definitions, strict bounded versioned JSON, immutable agent identity, content revision and compare-and-swap publication. GET/list, PUT and delete require ordinary live sessions, not special TestAccount. Do not copy the recovered proprietary RPC service or create another definition authority. Public contract is fabushi.automation.definition.v1, /v1/automations and /v1/automations/:automation_id; IDs share journal bounds. Definitions contain id, agentId, name, optional description, enabled, workflow. The workflow uses explicit trigger variant objects matching the existing Host cloud-definition projection and bounded prompts; non-clock trigger data is preserved for native ingress, not executed as code.
NAC-02: PUT requires exactly one of expectAbsent=true or baseRevision, with canonical content digest. An identical retry returns the stored receipt/revision, never rewinds the persisted clock. Different content with a stale precondition returns 409. Delete requires the current revision and keeps a tombstone; account/agent identity cannot move. Max 1000 live definitions/account and 64 KiB/definition. Unknown fields, invalid IDs/schedules/timezones fail before mutation. Native consumers retain explicit pending state after lost responses and reconcile GET, never blindly retry writes.
NAC-03: Core owns authoritative clock positions. Cron supports existing five fields, lists/ranges/steps, standard aliases, CRON_TZ/TZ and IANA timezone/DST; @every supports positive s/m/h/d including one second. Use explicit UTC when no timezone is provided. Preserve skipped/repeated local wall times as their actual UTC occurrences, and search eight calendar years for leap-day schedules. Local Host scheduling stays with its existing owner; cloud clock calculation does not select a second execution owner.
NAC-04: an account-scoped SQLite-backed Durable Object supplies wakeups, not definition/run truth. Its only durable data is the account ID and alarm. A small Core entry module preserves every existing Rust Worker handler, arms the object from trusted Rust response metadata, strips that metadata from public responses, and uses a fresh non-public per-invocation capability to call the Rust tick route. Public fetch removes any capability binding; arbitrary headers/bodies cannot forge internal tick access. No provider secret, user token, prompt or workflow is stored in the clock object. Normal Worker scheduled cleanup also reconciles due definitions as a bounded fallback; object delivery/retry is not execution. Cleanup failure must not prevent the clock fallback from being attempted. Bounded fallback selection rotates accounts by persisted last clock check, including capacity-blocked accounts, so an alphabetically earlier full account cannot starve later accounts. Clock checks do not change definition revision or user-visible publication time.
NAC-05: tick inserts deterministic run UUIDs bound to account/definition revision/trigger index/due timestamp and advances that cursor in the same D1 atomic batch with revision/current-cursor predicates. Duplicate alarm, response loss, shutdown/restart and simultaneous tick cannot create a second run or skip a quota-blocked occurrence. Events retain definition revision and scheduled timestamp. Clock delivery uses event=null so the existing Host schedule branch handles it; connector payloads remain reserved for source-specific events. Trigger index is bound in deterministic run identity, not misrepresented as a connector payload. Bound each tick, preserve backlog, and expose next alarm from persisted state. Disable/delete/revision change fences stale ticks. No timer invokes the Agent directly.
NAC-06: before native execution cutover, add authenticated session/device-bound claim/start/reconcile and durable Host intent/outcome history. Running/outcome-unknown must never expire back into executable work. Completion and ACK must preserve the existing immutable receipt/tombstone guarantees. Definitions/clock alone cannot enable shipping execution or establish NS-R1 completion.
NAC-07: all validation in Actions. Generate dependency locks only there, then commit the exact returned lock. Prove real wasm + D1 + Durable Object clock behavior, account/revocation/CAS isolation, 1-second @every, timezone/DST/leap-date math, duplicate alarms, restart, response loss, quota retention, disable/delete and internal-route forgery refusal. Injected clock/SQL tests are separate from actual-runtime and deployed evidence.
NAC-08: additive migration and normal protected deployment only after reviewed live pending/schema inventory and exact-source checks; existing recovery bookmarks, signing keys and provider variables remain intact. Introduce only the reviewed clock namespace/migration in the existing Worker, not a separate paid provider or service. Rollback preserves definitions/cursors/run tombstones and never restores Cursor. Full completion still requires native connector ingress, device execution, cloud Agents, file/share and signed installed-package/network acceptance.

## First implementation unit: durable automation run journal (protocol fabushi.automation.v1)
This establishes the previously missing completion contract. It does not complete scheduler/cloud Agent/file-service migration.
- POST /v1/automation-runs creates an account-owned event using runUuid, sandAgentId (legacy field name only), automationId, timestampMs, optional definitionRevision/scheduledForMs/event. Explicit owner manual enqueue only; external connector ingress remains under its existing trusted adapter.
- POST /v1/automation-events/poll takes ackRunUuids (max 100), returns unacknowledged events and bounded nextPollAfterMs. Acknowledgement mutates only account-owned completed rows. Unknown/not-completed ACKs fail atomically, never delete pending runs.
- POST /v1/automation-runs/complete takes runUuid,status (succeeded|failed),errorMessage. First completion persists atomically; identical retry returns the same receipt (200 JSON). Conflicting completion returns 409 without mutation. Missing or foreign run returns indistinguishable 404. Revoked/expired session returns 401. This protocol never returns 204.
- GET /v1/automation-runs/:run_uuid returns current account-scoped event, completion and ACK state for restart reconciliation. No automatic replay from outcome-unknown; Desktop must reconcile durable execution history before deciding to execute.
- UUID identity is account-scoped, request fields bounded and strict. Same runUuid with identical canonical event is idempotent; different event conflicts. Receipt is stable canonical completion digest plus stored completion time, not a client assertion of success.
- Durable PLATFORM_DB tables keep terminal tombstones; poll ACK does not erase idempotency history. Delivery is at-least-once; account-scoped polling is not a device lease. Before multi-device execution cutover add device/grant lease arbitration. Do not claim exactly-once side effects.

## Architecture and plan
Add one small automation domain module under the existing Worker and one additive migration; use authenticated_session_account, canonical JSON digest and D1 transactions/batches/CAS. Keep domain validation/transition functions testable on host, exercise SQL on actual SQLite in Actions, compile actual wasm routes. Desktop retains its existing Automations execution owner. Native transport must use explicit native credentials and paths; never generic Cursor/Sand token access. Deploy migration and service before enabling product cutover. Then close schedule/lease/recovery and remaining NS-R1..R4 units.

## Failures and observability
All failure responses retain work and expose typed error codes without tokens/event contents in logs. D1 failures are non-success. Duplicate/response-loss/restart tests must read canonical receipts. Cross-account identifiers do not disclose existence. Row limits and bounded event size protect storage; retention/quotas before production release. No pairing mutation is needed by this journal unit.

## Agent/file owner reconciliation decision
Read-only source and production probes on 2026-10-24 show the Node AccountSyncStore endpoint on ai.ombhrum.com exists and requires native account authorization, while the public api.ombhrum.com equivalent falls through Core and returns 404. Select the existing Node AccountSyncStore as remote file/account-state owner and add a narrow Backend gateway; do not port the unverified Desktop Worker copy or create duplicate Core tables. Core remains the native account/automation/device owner and Desktop the local file/execution consumer. This corrects the initial broad assumption that every service's state must be newly stored in Core. Live account file parity remains unverified.
